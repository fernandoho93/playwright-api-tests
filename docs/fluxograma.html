PLAY-API · GUIA DO PROJETO

Da requisição à evidência

Explore o caminho de execução dos testes de API com Playwright. Clique em cada etapa para ver sua função e os arquivos envolvidos. Também é possível usar Tab e Enter.

Este guia funciona offline. Ele explica o projeto; não executa testes nem faz chamadas às APIs.

1. Iniciar a execução

No terminal, npm test chama o Playwright pelo script do package.json.

No GitHub, .github/workflows/playwright.yml instala as dependências e executa os testes em pushes e pull requests para main ou master.

↓
2. Carregar a configuração

playwright.config.js define a pasta tests/, a URL base do Restful Booker e o relatório HTML.

Hoje, os 10 cenários são repetidos em chromium, firefox e webkit: 30 execuções. Para uma execução de cada cenário, use npm test -- --project=chromium --workers=1.

No CI há um worker, até duas novas tentativas por falha e bloqueio de test.only.

↓
3. Selecionar os cenários em tests/
  • consultar-reservas.spec.js: 3 cenários de consulta (CT01–CT03).
  • criar-reserva.spec.js: 2 cenários de criação (CT04–CT05).
  • dummyjson.spec.js: 1 cenário de produto (CT06).
  • example.spec.js: 4 exemplos de consulta (CT07–CT10).

Esses IDs são referências da documentação BDD. Cada cenário é independente; a ordem acima é apenas uma organização didática.

↓
4. Preparar dados e enviar a requisição

A fixture request envia GET ou POST diretamente por HTTP. Os testes não abrem páginas no navegador.

O CT02 cria uma reserva e usa o ID retornado na consulta. Outros cenários ainda dependem dos IDs fixos 1 e 695.

↓ para a API usada pelo cenário
Restful Booker

GET /booking
GET /booking/{id}
POST /booking

A URL base está na configuração. As reservas criadas ainda não são removidas.

DummyJSON

GET /products/1

A URL completa é montada no próprio teste de produto.

↓ resposta HTTP
5. Validar status e content-type

Os cenários atuais esperam status 200 e content-type contendo application/json.

Essas verificações acontecem antes de ler o corpo como JSON. Se falharem, o teste para nesse ponto. O CT07 termina suas validações aqui.

↓ quando o cenário valida o corpo
6. Ler o JSON e verificar os dados

response.json() transforma a resposta em dados JavaScript. As asserções verificam listas, campos, tipos ou igualdade com o conteúdo enviado, conforme o cenário.

Por exemplo: CT03 verifica presença de campos; CT08 verifica tipos; CT02 compara a reserva consultada com os dados da criação.

↓ resultado das verificações
Passou
Todas as verificações do cenário foram atendidas.
Falhou
Uma verificação ou requisição apresentou erro. Consulte os detalhes no relatório.
↓
7. Consultar logs e relatório

O terminal mostra resumos. Alguns testes adicionam corpos ou headers como anexos JSON ao longo da execução; a disponibilidade depende de quais etapas foram alcançadas.

npm run report abre o relatório de playwright-report/. No GitHub Actions, o workflow está configurado para guardar esse relatório como artefato por 30 dias.
